# kadet-hub Backstage plugins: Scaffolder

Status: Draft
Code: `plugins/scaffolder-backend-module-kadet-hub/`, `templates/recipe/`, `renovate.json` (BS-16), `.github/workflows/ci.yml`
Verified against: main @ e44a804

Related: kadet-hub/registry [consumers.md](https://github.com/kadet-hub/registry/blob/main/docs/specs/consumers.md) (CON-2, CON-4, CON-5), [recipes.md](https://github.com/kadet-hub/registry/blob/main/docs/specs/recipes.md) (REC-13), [catalog.md](https://github.com/kadet-hub/registry/blob/main/docs/specs/catalog.md) (CAT-34d).

## Problem

Platform teams offer "new service" flows as Backstage Software Templates. A
team that wants immich, gitea or wordpress from such a flow gets a Helm chart
today, because no Backstage plugin or template knows Kapitan or kadet-hub. The
Backstage plugin directory has no entry for any tool that generates
configuration: Helm, Kustomize, Tanka, Timoni, KCL and Kapitan are all absent.

Adding a recipe by hand means editing two inventories. The consumer copies
version and digest from the catalog into a fetch inventory, adds every
included recipe at exactly the digest the record lists, and writes a target
that includes `recipes.<name>`. An include at the wrong digest fails the
consumer workflow (CON-4 step 3). Copying from `catalog.json` is acceptable
only because the workflow verifies afterwards (CAT-34d).

Demand is not the reason for this spec. On 2026-11-05 no issue in
kapicorp/kapitan mentioned Backstage, and tool-specific scaffolder modules in
the directory had a median of 1,357 npm downloads per 28 days. Roadie's Argo
CD scaffolder module had 1,168. The plugin is a low-cost way to reach teams
that do not use Kapitan yet, so its scope stays at one backend action and one
template.

## Decisions

- DEC-1: The only feature is a scaffolder backend module with the action
  `kadet-hub:recipe:add`, plus one Software Template that runs it and opens a
  pull request. There is no entity provider, entity tab or catalog page.

  The scaffolder is the one feature whose user does not already run Kapitan.
  The others serve teams that use Kapitan inside Backstage, and none were
  found.

- DEC-2: The action reads the index from the GitHub release `index-<serial>`
  of kadet-hub/registry and verifies its Sigstore bundle in-process. It never
  pins from `catalog.json`.

  kadet-hub.org serves only the unsigned `catalog.json`. The release assets
  download anonymously over HTTPS, while the OCI index on ghcr.io needs a
  registry token exchange and the GitHub attestations API.

- DEC-3: The pull request is the delivery, and the consumer workflow stays the
  trust anchor. The action writes only digests the attested index lists. The
  recipe artifact's own attestation is checked by CON-5 when the pull request
  runs.

- DEC-4: The package is a backend module for the new backend system. A
  frontend package, if one follows, targets the new frontend system, which
  create-app has generated by default since 0.8.0.

- DEC-5: The code lives in kadet-hub/backstage-plugins, is published to npm
  as `@kadet-hub/backstage-plugin-scaffolder-backend-module-kadet-hub`, and is
  listed in the Backstage plugin directory after its first npm release.
  Decided 2026-11-05, formerly OQ-1.

  A repository of its own keeps the registry, which holds the release
  workflow, free of a Node toolchain of about 1,800 locked npm packages, and
  lets the plugin follow Backstage's monthly releases. backstage/community-plugins
  requires evidence of community demand, which kadet-hub cannot show yet.

## Index verification

The action resolves the newest tag once per run from the redirect of
`https://github.com/kadet-hub/registry/releases/latest` and downloads
`index.json` and `index.json.sigstore.json` from that tag. Index releases can
follow each other within minutes: index-109 to index-113 were published
within three hours on 2026-11-05. Two downloads from `latest/download` could
therefore come from different serials.

sigstore-js checks the bundle against the Sigstore public-good trust root,
which it fetches through TUF and caches in `$XDG_DATA_HOME/sigstore-js`. The
index bundles are Sigstore bundle v0.3 with a Rekor entry, because
kadet-hub/registry is public. `gh attestation verify --owner kadet-hub` also
checks the source repository owner extension. The action relies on the exact
certificate identity, which only a workflow of kadet-hub/registry on `main`
can obtain.

- BS-1: The action MUST verify `index.json.sigstore.json` with issuer
  `https://token.actions.githubusercontent.com` and certificate identity
  `https://github.com/kadet-hub/registry/.github/workflows/release.yml@refs/heads/main`.
  It MUST fail unless the bundle's in-toto statement has predicate type
  `https://slsa.dev/provenance/v1` and a subject whose sha256 equals the
  downloaded `index.json`.

  This is the check that `gh attestation verify` with `--bundle` runs in
  kadet-hub/registry `docs/consumers.md`.

  - Test: `recipe.test.ts` (`verifyIndex`: accepts index-113, rejects one appended byte, rejects another identity)
  - Since: this change

- BS-2: The action MUST fail when the index serial is lower than its input
  `minSerial`.

  This carries the replay protection of `index_serial` (CON-2) into
  Backstage. OQ-6 decides where the template takes the value from.

  - Test: `recipe.test.ts` (`refuses an index older than minSerial`)
  - Since: this change

- BS-3: The action MUST pin the requested version, or without one the highest
  version that is not yanked. It MUST fail on a version the index does not
  list or lists as yanked.

  Versions are compared as `X.Y.Z` integers, the form a recipe's
  `source.tag` allows (REC-1).

  - Test: `recipe.test.ts` (`pickRecipe`)
  - Since: this change

- BS-4: The action MUST fail unless every entry of the record's `includes` is
  listed in the index under its name and version, with the same digest, and
  not yanked.

  CON-4 step 3 fails the pull request otherwise. Failing in Backstage gives
  the error before a pull request exists.

  - Test: `recipe.test.ts` (`refuses an include whose digest the index does not list`)
  - Since: this change

- BS-5: The action MUST NOT accept a digest as input.

  The digest comes only from the verified index. A template input or
  `catalog.json` could name any digest.

  - Test: none (the input schema has no digest field)
  - Since: this change

## Files and policy

The action writes into the scaffolder workspace, which
`publish:github:pull-request` turns into a pull request. Each recipe gets its
own fetch target, `fetch/targets/<recipe>.yml`, so the action never rewrites a
fetch target the repository already has. Includes shared by two recipes are
then pinned in two files. That is valid while the digests agree, and BS-9
covers the case where they do not.

The recipes in kadet-hub/recipes are tested on the omegaconf backend only.
With reclass and reclass-rs, `kapitan inventory` fails on an immich target
with `Class recipes.cluster not found`, because `postgresql/init.yml` includes
the relative class `.cluster`. Neither the backend nor a recipe's required
parameters are in the index record (OQ-2), so the action names omegaconf in
its policy lines as a marked shortcut.

- BS-6: The action MUST write `fetch/targets/<recipe>.yml` in the shape CON-4
  step 2 accepts, `fetch/classes/.gitkeep`, and `inventory/targets/<target>.yml`
  with the class `recipes.<recipe>`, `parameters.namespace` and
  `parameters.kapitan.vars.target` set to the target name.

  The fetch target holds only `parameters.kapitan.dependencies`, one `oci`
  entry per recipe and per include, with source
  `ghcr.io/kadet-hub/recipes/<name>:<version>@sha256:<digest>` and
  `output_path: inventory/classes/recipes/<name>`. The reclass backends need
  the `classes/` directory next to `targets/`.

  - Test: `recipe.test.ts` (`writes the target and a fetch inventory pinned by digest`); manual: Kapitan 0.36.3 fetch of the dry-run output (2026-11-05)
  - Since: this change

- BS-7: The action MUST NOT overwrite a file in the workspace, and MUST
  resolve every path inside the workspace.

  - Test: `recipe.test.ts` (second run fails with `EEXIST`)
  - Since: this change

- BS-8: Recipe and target names MUST match `^[a-z0-9][a-z0-9-]*$`, in the
  action's input schema and in the template's parameter schema.

  Both become path segments. The template rejects `../evil` with HTTP 400
  before the action runs.

  - Test: manual: scaffolder dry run with target `../evil` (2026-11-05)
  - Since: this change

- BS-9: When the workspace holds the repository's fetch inventory, the action
  MUST fail if any fetch target pins one of the recipes it writes at another
  digest.

  - Test: none
  - Since: not implemented

- BS-10: The target MUST set every parameter the recipe record lists as
  required, from template input, and MUST write secret values as refs.

  An immich target fails `kapitan inventory` on omegaconf with
  `Interpolation key 'applications.valkey.password' not found` until that ref
  is added. Blocked by OQ-2.

  - Test: none
  - Since: not implemented

- BS-11: The action MUST NOT change `.kapitan-sandbox.yaml`. It MUST output
  the policy lines the repository needs: `fetch_inventory`,
  `inventory_backend`, `index_serial` and the record's `output_capabilities`
  for `compiled/<target>/*`.

  The policy is a security decision taken in review (CON-1b). The template
  puts the lines into the pull request body, where the reviewer adds them.

  - Test: manual: scaffolder dry run, pull request body (2026-11-05)
  - Since: this change

- BS-12: The action MUST support dry run.

  It only writes into the workspace, so the template editor can show the
  files without opening a pull request.

  - Test: manual: `POST /api/scaffolder/v2/dry-run` (2026-11-05)
  - Since: this change

## Template

`templates/recipe/template.yaml` asks for recipe, target name and repository,
runs `kadet-hub:recipe:add`, then `publish:github:pull-request` on branch
`kadet-hub/<target>`. A Backstage instance registers it by URL like any
catalog entity, so a new template version needs no npm release.

- BS-13: The repository MUST publish one Software Template that runs
  `kadet-hub:recipe:add` and `publish:github:pull-request`, and that puts the
  pinned reference, the index serial and the BS-11 policy lines into the pull
  request body.

  - Test: manual: dry run of the template in a Backstage 1.56 backend (2026-11-05)
  - Since: this change

## Release and directory listing

The package is pinned to Backstage 1.56.3 (`backstage.json`), with the
`@backstage` dependencies at the versions of that release's manifest as the
lower bound of a caret range, so a Backstage app dedupes them with its own.
`yarn.lock` pins every resolved version. `.yarnrc.yml` keeps the create-app
default `npmMinimalAgeGate: 3d`, matching Renovate's `minimumReleaseAge`, and
exempts `@backstage/*` as create-app does.

npm trusted publishing lets a GitHub Actions workflow publish through OIDC
without a token, and then adds provenance on its own. It needs npm 11.5.1 or
later, `id-token: write`, and a `repository.url` in `package.json` that
matches the GitHub repository. A trusted publisher can only be configured on
a package that exists, so the first version is published by hand.

The directory lists a plugin through a pull request to backstage/backstage
that adds `microsite/data/plugins/<name>.yaml`. CI validates it with
`scripts/verify-plugin-directory.js`. A quarterly audit marks a plugin
`inactive` after 365 days without an npm release, and `archived`, which hides
it, after a further year. `@backstage/plugin-scaffolder-node` is still 0.x, so
a monthly Backstage release can break the action.

```yaml
---
title: kadet-hub
author: kadet-hub
authorUrl: https://kadet-hub.org
category: Scaffolder
description: Adds a signed kadet-hub recipe to a Kapitan repository as a target pinned by digest, and opens a pull request.
documentation: https://github.com/kadet-hub/backstage-plugins/tree/main/plugins/scaffolder-backend-module-kadet-hub
npmPackageName: '@kadet-hub/backstage-plugin-scaffolder-backend-module-kadet-hub'
addedDate: 'tbd'
status: active
```

- BS-14: The package MUST be published to npm from a GitHub Actions workflow

  - Test: none

- BS-15: The directory entry MUST pass `scripts/verify-plugin-directory.js`,

  - Test: `node ./scripts/verify-plugin-directory.js` in a backstage/backstage checkout

- BS-16: The `@backstage` packages and `backstage.json` MUST move together,

  previous release and after every Backstage release that breaks its build or

  Renovate groups the `@backstage` packages with `backstage.json`, and the

## Acceptance criteria

- AC-1: A dry run of the template for `immich` in a Backstage 1.56 backend
  produces the three files with the digests of the attested index and a pull
  request body with the policy lines. Checks BS-1, BS-3, BS-4, BS-6, BS-11,
  BS-12, BS-13. Met on 2026-11-05 with index serial 113, in a scratch app

- AC-3: The consumer workflow passes CON-4 and CON-5 on a pull request the

## Alternatives

| Option                                                                                        | For                                                                                                  | Against                                                                                                    |
| --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Scaffolder module and template (DEC-1)                                                        | Reaches teams without Kapitan; verifies the index before the pull request; listable in the directory | npm package to maintain against monthly Backstage releases; needs OQ-2 for a target that compiles          |
| Templates generated by the registry release, served from kadet-hub.org, built-in actions only | No npm package and no Backstage version churn; per-recipe forms possible at build time               | Not listable in the directory; served unsigned; no verification before the pull request                    |
| Catalog entity provider per target                                                            | Kapitan targets as catalog entities                                                                  | Resolving a target needs Kapitan's Python inventory backends inside the Backstage backend; no demand found |
| Kadet generator that compiles `catalog-info.yaml` per target                                  | Same entities through Backstage's standard discovery, no plugin                                      | Helps only existing Kapitan users; not listable                                                            |
| Entity tab with parameters, compiled files, provenance                                        | Provenance next to the entity                                                                        | Needs the entity provider, read access to compiled output, and a frontend plugin                           |
| Catalog browser page in Backstage                                                             | Browse recipes without leaving Backstage                                                             | Duplicates kadet-hub.org                                                                                   |
| Code in backstage/community-plugins (DEC-5)                                                   | `@backstage-community` scope, shared CI and release tooling                                          | Requires demand evidence, monthly maintainer duties, volunteer review of 2 to 3 weeks                      |
| Code inside kadet-hub/registry (DEC-5)                                                        | Index format and action change in one pull request                                                   | Adds a Node toolchain to the repository that holds the release workflow                                    |

## Open questions

- OQ-2: How do a recipe's required parameters and its inventory backend get
  into the index record (REC-13)? Options are a schema file in the recipe
  directory checked by `check lint`, or fields parsed from the README's
  "Required parameters" section. Who owns the change: kadet-hub/recipes or
  the registry? BS-10 and AC-2 depend on it.

- OQ-3: Who creates and owns the npm organization `kadet-hub`? On 2026-11-05
  the npm registry had neither an organization nor a user of that name
  (`/-/org/kadet-hub/package` and `/-/user/kadet-hub/package` answered 404,
  as for an invented name, while existing ones answer 200), so the scope was
  free.

- OQ-4: Does the first release support GitLab
  (`publish:gitlab:merge-request`), given that the consumer flow has a GitLab
  template (CON-1a)?

- OQ-5: How does an air-gapped or proxied Backstage reach the index and the
  Sigstore TUF repository? Candidates are a configurable TUF mirror and cache
  path, and an index mirror.

- OQ-6: Should the template fetch the target repository first
  (`fetch:plain`)? That enables BS-9 and lets `minSerial` come from the
  repository's `.kapitan-sandbox.yaml`, but it needs a read token in the
  template.

- OQ-7: One generic template with a recipe picker, which needs a frontend
  field extension reading `catalog.json` and the OQ-2 fields, or one template
  per recipe generated by the registry release?

- OQ-8: Which release mechanism publishes to npm: Backstage's changesets, or
  a tag such as `scaffolder-backend-module-kadet-hub-vX.Y.Z` as kadet-hub/recipes
  tags its recipes? BS-14 depends on it.
